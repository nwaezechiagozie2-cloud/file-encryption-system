1. OVERVIEW & METHODOLOGY
================================================================================
This document records every software bug, cryptographic vulnerability, edge case,
and architectural defect discovered throughout the lifecycle of the File
Encryption and Decryption System.

The audit is strictly divided into two phases:
  - Part I (Before Building): Deficiencies found in the initial system design,
    baseline algorithms, and requirements before the production codebase was built.
  - Part II (After/During Building): Runtime errors, library incompatibilities,
    thread-safety bugs, edge-case crashes, and security vulnerabilities resolved
    during implementation, automated testing, and benchmarking.

2. PART I: FLAWS & DEFECTS IDENTIFIED BEFORE BUILDING (DESIGN & ARCHITECTURE)
================================================================================

--------------------------------------------------------------------------------
BUG/FLAW 1.1: Single-Iteration SHA-256 Key Derivation (Brute-Force Vulnerability)
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  The baseline design derived the AES encryption key using a single pass of SHA-256
  over the user's password: Key = SHA256(password). 
  Furthermore, no cryptographic salt was utilized.

- ROOT CAUSE & RISK:
  A single SHA-256 iteration requires minimal computation (nanoseconds on modern
  CPUs, and billions of evaluations per second on consumer GPUs). An adversary
  intercepting the encrypted file could execute high-speed dictionary and
  brute-force attacks. Without a unique cryptographic salt, identical passwords
  yield identical cryptographic keys, enabling precomputed rainbow table attacks.

- HOW IT WAS FIXED:
  Replaced single SHA-256 with PBKDF2-HMAC-SHA256 complying with RFC 8018 and
  NIST SP 800-132 recommendations:
  1. For each encryption, a cryptographically secure 16-byte random salt is
     generated using os.urandom(16).
  2. The iteration count is set to 100,000 rounds.
  3. PBKDF2 derives 64 bytes of total key material:
     - First 32 bytes (256 bits) assigned exclusively to the AES-256 cipher key.
     - Second 32 bytes (256 bits) assigned exclusively to the HMAC-SHA256 key.
  This forces an attacker to compute 100,000 SHA-256 rounds per guess per unique salt,
  neutralizing rainbow tables and rendering brute-force attacks computationally infeasible.

--------------------------------------------------------------------------------
BUG/FLAW 1.2: Lack of Authenticated Encryption (Padding Oracle & Bit-Flipping)
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  The original architecture relied solely on AES in Cipher Block Chaining (CBC)
  mode without any integrity verification mechanism or message authentication code.

- ROOT CAUSE & RISK:
  AES-CBC provides confidentiality but zero authenticity or integrity:
  1. Bit-Flipping Attacks: Flipping a bit in ciphertext block C_i results in a
     predictable bit-flip in plaintext block P_{i+1}. An attacker can alter
     sensitive contents (such as bank records or code) without detection.
  2. Padding Oracle Attacks: If an attacker modifies ciphertext bytes and observes
     whether the system returns a "padding error" or "decryption failed", they can
     systematically decrypt the entire file byte-by-byte without ever discovering
     the password.

- HOW IT WAS FIXED:
  Implemented the "Encrypt-then-MAC" (EtM) standard (RFC 7366):
  1. The file data is encrypted with AES-256-CBC.
  2. An HMAC-SHA256 authentication tag (32 bytes) is calculated across both the
     entire 64-byte binary header and the full ciphertext:
     Tag = HMAC-SHA256(HMAC_Key, Header || Ciphertext).
  3. The 32-byte tag is appended to the tail of the output file.
  4. During decryption, the system verifies the HMAC tag in constant time BEFORE
     attempting AES decryption or PKCS#7 unpadding.
  If a single bit is modified, the file is rejected immediately without performing
  decryption, completely neutralizing bit-flipping and padding oracle attacks.

--------------------------------------------------------------------------------
BUG/FLAW 1.3: Loss of Original File Extensions Upon Decryption
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  The baseline design merely appended `.enc` to the filename (e.g., `document.pdf.enc`)
  or stripped the extension. If a user renamed the file, encrypted a file without an
  extension, or transferred the file across operating systems, the software was
  unable to determine the original file type upon decryption.

- ROOT CAUSE & RISK:
  The file format metadata was not preserved within the encrypted package. Decrypted
  files were restored with generic names or missing extensions, requiring users to
  guess whether the file was a PDF, DOCX, ZIP, or PNG.

- HOW IT WAS FIXED:
  Engineered the binary file header to explicitly store the original file extension:
  1. The file extension (e.g., `.docx`, `.pdf`, `.png`) is extracted prior to
     encryption using os.path.splitext().
  2. The extension string is encoded into UTF-8 and padded with null bytes (`\x00`)
     into a fixed 16-byte field in the 64-byte header.
  3. Upon decryption, the software reads this field, strips null bytes, sanitizes the
     string, and automatically restores the original file with its correct extension.

--------------------------------------------------------------------------------
BUG/FLAW 1.4: Absence of Rigid Binary File Header & Magic Number Validation
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  The initial software design wrote raw ciphertext directly to disk without any
  file identification markers, versioning, or structural headers.

- ROOT CAUSE & RISK:
  Attempting to decrypt a non-encrypted file, a corrupt file, or a file produced by
  another tool caused unhandled exceptions, raw binary garbage output, or memory
  crashes. There was no way for the program to verify whether a given file was
  actually produced by this system.

- HOW IT WAS FIXED:
  Created a standardized 64-byte big-endian binary header using Python's `struct`
  module with the format string `!4sQI16s16s16s`:
    - Offset 00-03 (4 bytes): Magic Bytes `FED1` (File Encryption Device v1).
    - Offset 04-11 (8 bytes): Unsigned 64-bit integer storing the exact original file size.
    - Offset 12-15 (4 bytes): Unsigned 32-bit integer storing PBKDF2 iterations (100,000).
    - Offset 16-31 (16 bytes): Random PBKDF2 Salt.
    - Offset 32-47 (16 bytes): Random AES Initialization Vector (IV).
    - Offset 48-63 (16 bytes): Null-padded original file extension.
  On decryption, the software immediately checks the first 4 bytes. If they do not
  equal `b"FED1"`, it cleanly rejects the file with a specific `ValueError:
  "Invalid file format: missing FED1 magic header"`.

--------------------------------------------------------------------------------
BUG/FLAW 1.5: Missing Audit Trail and Operation Logging
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  The baseline design had no persistence or logging mechanism. Once a file was
  processed, no record remained of what was encrypted, when it was encrypted,
  what the original file hash was, or whether decryption attempts succeeded or failed.

- ROOT CAUSE & RISK:
  Users and administrators had no accountability, no forensic capability to detect
  unauthorized tampering or repeated failed decryption attempts, and no way to verify
  file integrity after processing.

- HOW IT WAS FIXED:
  Implemented a persistent SQLite logging engine (`app/db_logger.py`) that maintains
  a `local_audit.db` database.
  Every transaction records:
    - `id`: Auto-incrementing primary key.
    - `timestamp`: UTC ISO-8601 timestamp.
    - `operation`: 'ENCRYPT' or 'DECRYPT'.
    - `source_file`: Absolute path of the input file.
    - `dest_file`: Absolute path of the output file.
    - `original_size`: File size in bytes.
    - `file_hash`: SHA-256 checksum of the original unencrypted payload.
    - `status`: 'SUCCESS' or 'FAILED'.
    - `error_message`: Detailed exception description if failed.
  Both the GUI and CLI include dedicated audit viewing interfaces to review logs.

--------------------------------------------------------------------------------
BUG/FLAW 1.6: UI Thread Blocking on Cryptographic Operations
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  In standard single-threaded Tkinter desktop applications, executing long-running
  operations (such as 100,000 PBKDF2 rounds and encrypting files over 50 MB) directly
  in event handler callbacks blocks the main GUI event loop.

- ROOT CAUSE & RISK:
  The operating system marks the application as "Not Responding" (spinning beachball
  or greyed-out window). The user cannot cancel, see progress updates, or interact
  with the application, often leading them to force-kill the process and corrupt files.

- HOW IT WAS FIXED:
  Implemented multithreaded asynchronous task execution in `app/gui.py`:
  1. All cryptographic file processing is dispatched onto a background daemon worker
     thread (`threading.Thread(target=..., daemon=True)`).
  2. The main thread continues running the Tkinter event loop smoothly.
  3. Action buttons are disabled during processing to prevent re-entrant calls.
  4. An animated indeterminate progress bar gives immediate visual feedback.
  5. UI updates and completion alerts are routed back to the main thread safely.

--------------------------------------------------------------------------------
BUG/FLAW 1.7: Unsafe File Overwriting and Lack of Atomic Writes
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  Directly opening the destination file for writing (`open(dest, "wb")`) exposes
  the system to severe data loss if the computer crashes, runs out of disk space,
  or loses power halfway through writing.

- ROOT CAUSE & RISK:
  A half-written file is permanently corrupted. If the destination was overwriting
  an existing file, the existing file is destroyed with no possibility of recovery.

- HOW IT WAS FIXED:
  Implemented atomic file writing in `app/file_handler.py`:
  1. The output data is written to a temporary file (`tempfile.NamedTemporaryFile`)
     created in the exact same directory as the target destination.
  2. The file descriptor is flushed and synchronized to physical disk with `os.fsync()`.
  3. The temporary file is atomically moved to the destination filename using
     `os.replace()`.
  In POSIX and Windows filesystems, `os.replace` is an atomic directory operation;
  either the complete new file appears, or the original file remains untouched.

3. PART II: BUGS & ISSUES ENCOUNTERED & FIXED AFTER/DURING IMPLEMENTATION
================================================================================

--------------------------------------------------------------------------------
BUG 2.1: Missing 'Crypto.Util.Padding' Module (PyCryptodome vs PyCrypto Conflict)
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  When running the initial test suite on the Linux environment, Python threw:
    `ModuleNotFoundError: No module named 'Crypto.Util.Padding'`

- ROOT CAUSE:
  The host environment had legacy system packages where the top-level `Crypto`
  namespace was partially occupied or missing the modern PyCryptodome submodules.
  Relying solely on `from Crypto.Util.Padding import pad, unpad` created an external
  point of failure across different operating systems and Python versions.

- HOW IT WAS FIXED:
  1. Installed modern `pycryptodome>=3.18.0` via pip.
  2. In `app/crypto_engine.py`, implemented an autonomous fallback RFC 5652 PKCS#7
     padding and unpadding implementation directly in pure Python:
       - `_pkcs7_pad(data, block_size)`: Appends `(block_size - len(data) % block_size)`
         bytes, each set to that integer value.
       - `_pkcs7_unpad(data, block_size)`: Validates that the last byte value `P`
         is between 1 and `block_size`, and confirms all trailing `P` bytes equal `P`.
     If `Crypto.Util.Padding` is missing, the engine automatically falls back to this
     internal RFC 5652 implementation without throwing an exception or failing.

--------------------------------------------------------------------------------
BUG 2.2: PKCS#7 Padding Handling on Exact 16-Byte Block Boundaries
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  During boundary unit testing, files whose sizes were exact multiples of 16 bytes
  (e.g., 16 bytes, 32 bytes, 64 bytes) exhibited edge-case unpadding ambiguity.

- ROOT CAUSE:
  If a file has length 16 and is not padded with an additional 16-byte block, the
  unpad function cannot distinguish whether the final byte (e.g., `0x01` or `0x10`)
  is genuine user plaintext or padding.

- HOW IT WAS FIXED:
  Enforced strict PKCS#7 standards across all pad/unpad routines:
  When `len(data) % 16 == 0`, a complete new 16-byte block of `\x10` (16 bytes of
  decimal 16) is appended. On decryption, the unpadding routine safely strips all
  16 padding bytes, restoring the exact 16-byte original plaintext.
  Automated tests for 0B, 1B, 15B, 16B, 17B, and 32B boundary sizes verify this behavior.

--------------------------------------------------------------------------------
BUG 2.3: Zero-Byte (Empty) File Edge-Case Failure
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  Attempting to encrypt an empty file (0 bytes) caused cryptographic pipelines to
  behave unpredictably or fail verification checks because `len(plaintext) == 0`.

- ROOT CAUSE:
  Certain libraries treat zero-length input as an error or fail to generate valid
  ciphertext blocks. Furthermore, reading an empty file could return EOF before
  headers were properly initialized.

- HOW IT WAS FIXED:
  In `app/crypto_engine.py` and `app/file_handler.py`:
  1. A 0-byte input is validly padded by PKCS#7 to 16 bytes of `\x10`.
  2. The 64-byte header explicitly records `original_size = 0`.
  3. AES-256 encrypts the 16-byte block, and HMAC-SHA256 tags the result.
  4. On decryption, the system decrypts the 16-byte block, unpads it to 0 bytes,
     confirms that decrypted length matches `original_size (0)`, and writes an
     empty 0-byte file.
  Unit test `test_encrypt_decrypt_empty_file` was added to verify zero-byte round-trips.

--------------------------------------------------------------------------------
BUG 2.4: Path Traversal Vulnerability via Header Extension Field
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  The 16-byte extension field stored in the binary header could theoretically be
  crafted by a malicious actor to include directory traversal sequences such as
  `../../../../usr/bin/evil` or `../bad.sh`.

- ROOT CAUSE:
  Directly concatenating the header's extension string to the output path without
  sanitization allows an attacker to write files outside the target directory.

- HOW IT WAS FIXED:
  Added a dedicated sanitization function `sanitize_extension()` in `app/file_handler.py`:
  1. Decodes the 16-byte field and strips trailing null bytes (`\x00`).
  2. Converts the string to lowercase and passes it through `os.path.basename()` to
     strip all folder separators (`/` and `\`).
  3. Replaces all characters outside the safe whitelist `[a-z0-9_.]` with an empty string.
  4. Truncates extension length to a maximum of 10 characters.
  5. If the resulting extension is empty or invalid, it defaults safely to `.decrypted`.

--------------------------------------------------------------------------------
BUG 2.5: SQLite Multi-Threading Concurrency Lock / Thread Affinity Error
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  When running GUI operations where the encryption/decryption was executed inside
  a worker thread, logging to SQLite caused:
    `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread.`
  Additionally, concurrent CLI or GUI operations could encounter `database is locked`.

- ROOT CAUSE:
  By default, Python's `sqlite3` connections cannot be shared across different
  threads. Retaining an open connection in `DBLogger.__init__` violated thread affinity.

- HOW IT WAS FIXED:
  Redesigned `app/db_logger.py`:
  1. Instead of storing an open persistent connection, `DBLogger` creates and closes
     connections per method call using context managers:
     `with sqlite3.connect(self.db_path, timeout=10.0) as conn:`
  2. Configured a 10-second busy timeout (`timeout=10.0`) to queue concurrent
     requests rather than throwing locking errors.
  3. Ensured `WAL` (Write-Ahead Logging) compatibility and explicit thread isolation.
  Both main and worker threads can now invoke `log_operation()` and `get_history()`
  concurrently without exceptions.

--------------------------------------------------------------------------------
BUG 2.6: Timing Side-Channel Vulnerability in HMAC Tag Verification
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  Initially, the HMAC verification logic compared the computed tag against the
  stored tag using Python's standard string equality: `if calculated_tag == expected_tag:`

- ROOT CAUSE:
  Standard equality checks terminate early on the first mismatched byte. An adversary
  measuring high-precision execution timings can deduce correct tag bytes one-by-one,
  enabling tag forgery without knowledge of the HMAC key.

- HOW IT WAS FIXED:
  Replaced standard equality with `hmac.compare_digest()`:
    `if not hmac.compare_digest(calculated_tag, expected_tag):`
         `raise ValueError("Authentication failed: HMAC tag mismatch or data corrupted.")`
  `hmac.compare_digest` executes in constant time regardless of where mismatches
  occur, eliminating timing side-channel leakage.

--------------------------------------------------------------------------------
BUG 2.7: Silent Overwrite Data-Loss Bug in CLI and GUI
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  In the initial build, specifying an output file that already existed on disk
  would silently overwrite and obliterate the existing file without asking the user.

- ROOT CAUSE:
  The application lacked pre-flight destination checks, creating a serious data-loss
  hazard if a user accidentally selected an important file as the output destination.

- HOW IT WAS FIXED:
  1. In `app/gui.py`: Added an explicit check before starting encryption/decryption:
     If the target file exists, a modal dialog (`messagebox.askyesno`) prompts:
     `"Output file already exists. Do you want to overwrite it?"`. If the user selects
     "No", the operation is cancelled safely.
  2. In `cli.py`: Added overwrite protection. If the target file exists, the command
     aborts with an error message unless the user explicitly passes the `-f` / `--force`
     flag.

--------------------------------------------------------------------------------
BUG 2.8: Unsanitized Password Input & Plaintext Password Exposure
--------------------------------------------------------------------------------
- PROBLEM DESCRIPTION:
  In early prototype testing of the CLI, passwords passed via terminal prompts
  echoed the plaintext characters onto the terminal screen. Furthermore, empty
  passwords were submitted without validation.

- ROOT CAUSE:
  Using standard `input("Enter password: ")` displays passwords in cleartext in the
  terminal and shell command history.

- HOW IT WAS FIXED:
  1. Switched to Python's `getpass.getpass()` module in `cli.py`, which masks keystrokes
     completely during input.
  2. Added password confirmation prompts during encryption (`getpass("Confirm password: ")`)
     to protect users from mistyped passwords.
  3. Added input validation in both GUI and CLI: empty or whitespace-only passwords
     are rejected immediately before cryptographic operations begin.
